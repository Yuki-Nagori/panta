# Qt 交互状态机（规划）

[模块导航](README.md) · [界面与桥接](../architecture/ui-and-bridge.md) · [Rust Flow](flow-state-machines.md) · [实施任务 074](../task/074-qt-interaction-state-machine.md)

更新 / 官方资料查阅日期：2026-09-24，Qt 文档版本 6.11.2。本模块尚未实现；当前导入窗口仍由 QML 函数与属性组织交互。

## 决策与分工

明确采用 Qt 自带的 `QStateMachine` 管理复杂 UI 交互，由 C++ ViewModel / 交互控制器持有，以导入窗口作为首个消费者。它是独立于 Rust Flow 的 UI 能力，不要求等待 `.pa` 生成器完成后才开始接入。

| 层次 | 负责内容 | 示例 |
|---|---|---|
| Rust 领域状态机 | 业务规则、输入快照、修订、资源所有权、提交和取消裁决 | 能否提交、工程是否已提交、工作是否已取消 |
| C++ `QStateMachine` | 本地交互流程、用户意图排序、等待服务回执、弹窗和关闭协调 | 选文件后进入预览等待，失败后保留表单以供重试 |
| QML 属性绑定 / `states / transitions` | 属性配置、视觉反馈、动画和简单局部状态 | hover、展开 / 折叠、错误颜色、等待提示 |

Qt State Machine 的 C++ 入口是 `Qt6::StateMachine`，也提供 `QtQml.StateMachine` QML API；它与 Qt Quick 的视觉 `State` 不是同一个 API。[Qt 模块文档](https://doc.qt.io/qt-6/qtstatemachine-index.html) 首期选择 C++ 入口，QML 只发语义意图、绑定只读交互属性。后续局部组件确需使用 QML API 时单独评估，不在 C++ / QML 各保存一份相同流程。

不把所有 UI 布尔值改成状态机，也不组合一个覆盖整个桌面的状态笛卡尔积。一个交互流程一个控制器；独立 Dock 显隐、Ribbon 页签和 hover 保持简单绑定。视口逐帧输入与渲染仍留在既有 C++ 后端，不为鼠标每帧事件引入全局状态图。

## 首个消费者：导入窗口

[`ImportDialog.qml`](../../qml/Dialogs/ImportDialog.qml) 当前直接处理窗口打开、选文件、预览调用、导入返回值及关闭。074 将这些交互入口集中到控制器，保留表单数据和布局；实际解析、校验与工程写入仍通过 `ProjectViewModel` 调用 Rust。

以下是交互阶段草案，不是 Rust 导入事务状态的复制；实施时按实际服务契约冻结：

| UI 阶段 | 进入原因 | 可接受的后续意图 / 回执 |
|---|---|---|
| Closed | 未打开或允许的关闭已完成 | 打开并初始化本次窗口会话 |
| Editing | 打开窗口、返回编辑或选文件前 | 浏览文件、修改选项、关闭 |
| ChoosingFile | 一次已接受的 Browse | 文件选择器接受 / 拒绝；拒绝恢复选择前的有效输入 |
| AwaitingPreview | 接受新文件并提交一次预览请求 | 对应预览结果、错误或关闭意图；旧预览不能开启 Submit |
| Ready | 当前输入的预览已确认 | 修改选项、重新选文件、提交、关闭 |
| AwaitingResult | 控制器已接受提交意图，等待派发 / 返回或异步业务结果 | 对应业务结果；关闭 / 取消能力按真实服务契约显示 |
| Error | 当前请求失败或展示刷新失败 | 按失败阶段提供重新预览、重试提交或仅刷新展示，不能统一重发导入 |

重新选文件时记录选择前的 UI 状态；取消文件选择器可恢复有效预览，接受新文件则使旧预览失效。选项是否需要重新预览由服务契约确定，Qt 不复制格式、单位或几何校验规则。提交按钮可用性由本地交互阶段和 Rust 提供的有效性 / 能力共同决定，Rust 仍需校验每个请求。

现有 STL 调用是同步接口，等待阶段可能在一次事件循环内完成；状态机不能使其自动后台化。074 首期验证 UI 流程与真实同步回执，073 后续提供真正的任务身份、进度、取消与提交回执后，再接入相应交互。提交前的 Cancel / Esc 仍可关闭表单或文件选择器，不调用业务取消；`AwaitingCancelReply` 等阶段只在实际服务支持时引入。没有业务取消能力时禁用的是在途任务的取消操作，不能因此禁用普通表单关闭。

## 事件、命令与生命周期

`QStateMachine` 依赖运行中的 Qt 事件循环，启动、停止和完成有不同的生命周期信号；不能在调用 `start()` 后立即假定初态已进入，`stop()` 也不代表完成业务。[QStateMachine 官方文档](https://doc.qt.io/qt-6/qstatemachine.html) 本项目规定控制器与状态对象留在 GUI 线程，长业务经服务调度，转移判断不执行文件 I/O 或长 native 调用。

- 对 UI 暴露稳定的交互 phase、能力和命令，不暴露 `QState*` 或任意设置状态的接口。启动未就绪时明确拒绝或排队意图，并验证其次数 / 顺序。
- 接受用户意图时就在 GUI 线程内占用本次请求并冻结参数，再请求状态转移；不能等目标状态的 entered 才阻止重复 OK / Browse。等待状态生效后才派发一次命令，异常退出或拒绝必须释放待发请求。同步回执也按本次关联在转移完成后处理，避免重入或结果早于目标状态。
- 同一次服务调用只有一个完成来源。当前 `inspectStl` 会发出预览清空 / 更新通知，`importStl` 会发出工程 / 资产通知；这些属性信号只更新读模型，不能又和返回结果各推进一次交互。适配层统一给出关联完成回执，并区分 Rust 命令被拒绝、命令成功与后续展示刷新失败；不能把所有 `bool == false` 都当成“工程未提交，可以重试”。已提交但刷新失败只能重读展示，不能再次导入。
- 状态进入只更新 UI 配置；业务命令必须来自明确接受的用户意图。初始化、组件重建和恢复快照不能自动再次导入、保存或取消。若实现用状态进入触发派发，必须消费一次性待发意图，恢复路径不创建该意图。
- 文件选择、预览及导入回执分别携带可验证的请求 / 窗口会话关联；异步业务再关联 TaskId 与工程 generation。关闭重开、重新选文件和过时结果不得污染当前表单。若底层信号不带 ID，控制器需限制同时在途请求并建立可靠的关联，不能猜测它属于当前会话。
- OK、Cancel、Esc、标题栏及系统关闭请求走同一控制器入口。等待提交期间只能按 Rust 能力请求取消或分离展示；Qt 的关闭 / stopped / finished 信号不得生成领域 `Cancelled / Committed`。原事务继续由 Rust 拥有者收尾，具体规则沿用 [Flow 事务设计](flow-state-machines.md)。
- QObject parent 和有上下文的连接管理所有权，销毁前断开投递；计时器、延迟事件和回调不能引用已销毁的窗口。首期控制器及所需表单草稿由窗口之外的同一 ProjectViewModel 会话拥有，不能把 Rust 工程快照当作尚未提交的文件路径 / 选项草稿。普通窗口重建保留该服务会话，先读取当前业务快照，再结合仍有效的 UI 草稿恢复；主动关闭后清空还是保留草稿由交互契约明确。整个 ProjectViewModel / QQmlEngine 销毁后的服务延续不属于 074 首期承诺，027 与 073 按实际所有权另行衔接；不能跨引擎搬运 QObject / JS 值，也不能依靠 `QHistoryState` 充当业务恢复。
- 交互属性只有控制器一个写入者，QML 以绑定消费；视觉状态不覆盖控制器的业务等待标志。表单字段有自己的明确所有者，避免 QState 属性赋值与 QML 绑定相互覆盖。

## 模块供给与实施边界

当前 [`native/CMakeLists.txt`](../../native/CMakeLists.txt) 查找 Core / Gui / Qml / Quick 等组件，未加入 StateMachine；[`qt-provision.cmake`](../../native/cmake/qt-provision.cmake) 只登记了现有 Qt 基础、声明式、工具与 SVG 归档。074 必须核实三平台 StateMachine 实际归档及依赖并固定哈希，再由 CMake 查找并链接 `Qt6::StateMachine`。本次没有下载或验证新制品，不承诺现有缓存已经包含该模块。

首期不引入 `QtQml.StateMachine` import，因此不额外承诺部署它的 QML 插件；若以后使用该 API，再同步 import 扫描、qmllint、插件与安装产物。采用 Qt 状态机不要求引入 SCXML 文件，也不改变 `.pa` 只描述 Rust 流程结构的决定。

074 先交付模块接入、导入 UI 控制器和现有服务的真实回归；073 独立交付 Rust 异步事务，二者共享语义命令 / 快照 / 回执契约，不共享运行期状态机对象。普通销毁重建属于 074 验收，开发模式 QQmlEngine 重载仍由 027 负责。Qt 模块只是这一项功能的依赖，不让它成为所有 UI 或 Rust 功能的新前置条件。

## 验证重点

用 QtTest / GTest 与 QML 行为用例观察状态、命令次数和信号顺序，覆盖未启动就绪、状态尚未转移时连续点击、同步多次属性通知与唯一完成回执、提交后刷新失败、旧选择 / 旧请求回执、表单关闭和同一服务会话内窗口销毁重建。恢复 UI 后再次观察命令计数，确保没有业务重放。带延迟的测试后端只验证交互，不作为真实异步业务或 GPU 窗口验收证据；TaskId、业务取消和完整引擎重载验收留在实际异步 / 重载功能联调阶段。

最终使用仓库 Cargo 聚合入口，并验证真实窗口、模块部署和三平台构建；完整命令与验收条件见 [074](../task/074-qt-interaction-state-machine.md)。
