# 应用平台、Rust 与工程存储

[架构总览](README.md)

路径与运行时上下文（023/024）及变量 DSL（025）已实现；其职责和限制见[路径与运行时](../modules/paths-and-runtime.md)、[变量 DSL](../modules/variable-dsl.md)。这些能力不构成通用虚拟机。

## Rust 的职责

Rust 负责工程、工作区、命令、序列化和后台操作状态；当前工程操作的调度由私有 `ProjectExecution` 提供。工程撤销/重做模型、统一任务 / 作业服务和求解器客户端尚未实现，待真实业务形成共同需求后设计。插件体系是长期方向，V1 不要求先实现插件加载平台。C++ 负责 Qt 桥接以及几何、网格和渲染的 native 实现。

Bridge `Settings` 通过 Rust 设置服务管理应用偏好，并由 Qt adapter 使用 `QSettings` NativeFormat 持久化单一版本化快照。主题 ID、语言、窗口逻辑尺寸与最大化状态、最近工程路径属于用户偏好；工程数据和临时视口状态不混入其中。损坏设置保留原存储、回退内存默认值并报告诊断；持久化失败保留最近一次有效内存状态。设置 schema 和边界见[任务 125](../task/125-settings-service-and-qt-adapter.md)，语言设置界面由[087](../task/087-language-settings-ui.md)负责，平台菜单入口由[115](../task/115-platform-application-menu-and-settings-entry.md)规划。主题视觉 token 由 030 的 `.pa` 提供，设置只保存主题 ID。

应用服务将用户命令转换为跨模块操作；Rust 与 C++ 之间优先传递明确所有权的 DTO、句柄和结果。工程创建、读取、保存、重命名及 STL 导入等路径已通过 CXX 接入；稳定错误码和线程边界见[职责审计](native-domain-boundaries.md)。字符串编码、缓冲区归属、释放接口、线程约束和错误映射必须明确，异常与 panic 不得未经处理跨越 FFI 边界。GUI 的文件读取与资产激活已有后台入口，CLI 保持同步。

工程服务按状态/清单、诊断、存储、工作区、缓存和用例模块拆分；公开 `panta_core::project` 门面保持服务调用边界。具体目录归属见源码，模块职责见[命令层](command-layer.md)。

工程 revision 是过期请求的相关性键，递增通过单一检查入口完成。达到 `u64::MAX` 后拒绝需要新修订的变更，在修改内存、写入资产或启动候选提交之前返回错误，不能以饱和成功让不同状态共享同一修订。

## 工程模型

工程应组织元数据、几何资产、网格、材料、Studies、作业记录与结果引用。每个实体具有工程内稳定 ID，派生实体记录来源修订。模型状态与窗口布局、临时选中项等会话状态分开存储。

工程 dirty 状态来自已接受的领域变更。视口旋转是否持久化可以单独定义，不能让每一帧渲染都产生工程命令。Study 和 Job 区分：Study 是可编辑配置，Job 是某次固定输入快照的执行记录。

## 命令、任务与作业

命令表示可验证的用户操作。未来若引入任务模型描述后台执行、作业描述求解运行，应在开始时固定输入快照，避免执行期间读取到不断变化的工程。

FSM 只在构建期声明结构，Rust 实现业务行为。导入准备归 `panta-import`，工程事务与资产激活由 `panta-core` 协调；准备完成不等于提交成功，工程发布成功后才能进入 `Committed`。取消 / 提交裁决、迟到结果与关闭后失效由 Rust 处理，Qt 仅消费展示快照。工程 I/O 由私有 `ProjectExecution` 有界调度，具体操作状态由领域服务维护；容量、取消和退出收尾见[任务 109](../task/109-bounded-background-execution.md)。当前没有通用 TaskManager 或共享任务 / 作业 API。

撤销/重做适合工程模型变更。大型资产可以保存引用或修订，避免每步复制整个网格。外部求解进程已执行的计算不能靠撤销命令“倒退”；撤销只能调整本地配置或引用，取消作业是独立操作。

## 存储契约

工程目录包含 schema 4 的 `.panta` 清单与 `assets/meshes/` 资产。来源路径、格式、哈希、mtime 与大小仅作为诊断快照；不复制原始 STL，运行时也不依赖来源路径。开发阶段只接受 schema 4，旧 schema 明确拒绝。工程格式与来源策略的详细契约见[任务 088](../task/088-mesh-asset-sidecar-storage.md)。

工程写入由 repository 租约串行化：同一工程的服务实例通过 fs4 锁协调，清单与 Mesh sidecar 使用共同提交边界，失败保留旧清单和旧资产。该锁为协作式；文件同步和崩溃保证的具体边界见[任务 108](../task/108-project-write-coordination.md)。

分析序列当前按导入记录 ID 保存在清单覆盖表；它描述后续分析设置，不代表已生成对应网格。契约与验证见[任务 092](../task/092-plan-analysis-sequence-and-mesh-settings.md)。

工程打开只读取索引；Mesh 在页签激活时解码、校验并进入 Rust 运行期缓存，再以批量 DTO 提供给 VTK。持久化格式、压缩与容量提醒等由 088 维护，显示对象和 GPU 资源不写入工程。

未来求解结果及其他大型资产仍需定义可移交的嵌入或外部引用策略。读取时对缺失资产、未知 schema 版本、损坏数据及单位不一致提供明确诊断。

多文件断电原子性与目录项断电持久性不保证。工程格式不做隐式旧版迁移，遇到不支持的 schema 明确拒绝；如确有迁移需求，按[代码生命周期规范](../standards/code-lifecycle.md)另行登记。

## 大数据与缓存

Mesh、结果按用户打开的页签、时间步、区域或字段延迟读取，缓存有容量与失效策略。缓存可由已提交资产重建，不能作为唯一数据源。关闭页签释放该页签独占的 CPU Mesh 快照和 VTK 显示对象；关闭工程时取消读取、释放映射和资源。结果文件仍在写入时，仅开放已经正式发布的完整片段。Mesh 快照容量和逐出阈值由 080 / 088 的代表性测量确定，不由 GPU RSS 单项推导。

验收重点是保存/重开后 ID 与引用一致、资产缺失可解释、写入失败保留旧工程，以及旧任务不能污染新打开的工程。
