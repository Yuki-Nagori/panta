# [External / 非本仓库] Mold Protocol 共享契约

[架构总览](README.md)

## 归属与状态

`mold-protocol` 是方案中按需建立的第三个小型仓库，不是已经确认存在的依赖。它可能统一维护 mold-schema、solver-protocol、simulation-format；这些名称表示契约领域，不表示已发布的包。

在独立仓库建立前，应明确临时权威来源和版本；建立后由两端引用相同发布版本或生成产物。本仓库的 `schemas/` 不得成为与上游并行演进的另一份权威定义。

## 契约分层

1. **分析输入 schema**：网格引用、材料、工艺、边界条件、求解选项以及单位约定。
2. **控制协议**：启动/取消请求、能力协商、错误、进度、迭代、时间步与完成事件。
3. **数据格式**：几何/网格/字段的资产描述、关联关系、时间序列、分块读取和完整性信息。

控制协议编码和大型结果存储格式可分别选择。protobuf 或 gRPC 不能自动解决大型数组布局、单位、节点顺序和文件提交语义；这些都需要单独定义。

## 身份、版本与兼容性

工程实体 ID、作业 ID、资产 ID 和数组索引具有不同用途，不能互换。定义字段关联到节点还是单元、分量顺序、坐标系、单位、索引宽度、字节序及缺失值表示，保证两个进程对相同数据有一致解释。

协议版本和数据格式版本分别管理；握手提供能力信息。需明确未知可选字段的处理、必选能力缺失时的拒绝方式、枚举扩展策略，以及破坏性变更的升级规则。版本号的具体格式尚未确定。此处说明外部契约需定义的行为，不授权本仓库默认实现跨版本兼容；客户端默认拒绝不支持版本，确需例外按 [代码生命周期规范](../standards/code-lifecycle.md) 登记。

## 结果发布与一致性

定义资产什么时候可读、部分结果怎样标识、完成事件保证什么，以及取消/失败后哪些数据仍有效。对于分时间步输出，每一步应能独立声明完整，不能靠文件存在判断写入完成。

共享内存若被采用，还需规范进程间同步、所有权和释放握手；远程资产则需独立的位置与传输约定。本地路径仅对共享相同文件系统的参与者有效。

## 协作验证

维护最小请求/事件样例、标准网格/字段夹具、合法与非法输入，以及至少一组客户端/服务端兼容性用例。生成代码要可复现，并注明生成器版本。双方升级时运行契约测试，避免各自测试通过而交互失败。

正式协议字段需要在实际实施时共同评审，本文件是边界规划，不是可以直接实现的完整 wire specification。
